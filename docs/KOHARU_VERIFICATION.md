# 코하루 루트 구현 검증 기록

이 문서는 히든 히로인 코하루 루트를 게임에 넣은 뒤, 이 저장소에서 실제로 실행한 검사와 그 결과를 적은 것이다.

- 대상: 브랜치 `ccr-9f825d9d-xvarye`, 커밋 `52091e8`(1단계 구현)에 E2E 갱신·검토 수정을 더한 작업 트리. 이 문서와 같은 커밋으로 들어갔다(그 뒤 README 링크 한 줄과 UI_DESIGN 의 임시 경로 표기만 고쳤다). 대본 버전은 `STORY.version` 0.2.0 이다.
- 날짜: 2026-11-25
- 환경: Linux, Node.js 22.23.5, TypeScript 5.9.3, Vite 8.3.8, Vitest 5.1.1, Playwright 1.63.0(Chromium 빌드 1243, WebKit 빌드 2359)

인계 패키지에 든 `docs/VALIDATION.md`(「코하루 대본·그림 검증 기록」)와는 다른 문서다. 그 문서는 납품 그림·원고·분기 설계를 검사한 기록이다. 실제 게임 엔진과 브라우저에서 돌린 결과는 이 문서에만 있다.

## 2. 분기 분포(`npm run validate`)

검사기는 실제 실행기(`settle`·`choose`·`visibleOptions`)로 보이는 옵션의 모든 조합을 돌린다. 계약 규칙으로 따로 쓴 오라클과도 대조한다. 출력은 다음과 같다.

```
장면 34개 · 대사 706줄 · 선택지 7개 · 선택 조합 2187개
분기 분포: 경로 2187 · 초반 조합 81(해금 25) · 해금 경로 675/미해금 1512 · 엔딩 아카네 999 / 히나 999 / 코하루 189 · 동점 처리 146(해금 42/미해금 104)
  · 아카네 루트 (999개 조합): 본편 221줄/7152자 ≈ 13.0~18.8분 · 후일담 55줄/1711자 ≈ 3.1~4.5분
  · 히나 루트 (999개 조합): 본편 219줄/7176자 ≈ 13.0~18.9분 · 후일담 54줄/1908자 ≈ 3.5~5.0분
  · 코하루 루트 (189개 조합): 본편 246줄/7987자 ≈ 14.5~21.0분 · 후일담 102줄/3582자 ≈ 6.5~9.4분

✔ 스토리 검증 통과
```

기대값(2,187 경로, 초반 81조합 중 해금 25, 엔딩 999 / 999 / 189, 동점 처리 146)과 같다. 미해금 경로 1,512개에서 코하루 흔적(화자·그림·CG·배경·치환 키·k 옵션)이 실행되면 검사기가 오류를 낸다. 이번 실행에서 오류는 없었다.

## 4. 세 엔딩 재현 방법

새 게임에서 공통 선택 7번(`c3.ch` `c4.ch` `c6.ch` `c7.ch` → `c8.ch` `c9.ch` `c10.ch`)을 아래 순서로 고른다. 초반 옵션은 a=아카네, b=히나, c=셋이 함께다. 후반 옵션은 a=아카네, b=히나이고, 셋째 칸은 해금 플레이면 k=코하루, 아니면 c=함께다. 루트에 들어간 뒤 선택지는 어느 것을 골라도 엔딩이 같다.

| 엔딩 | 선택 순서 예 | 점수 흐름 |
|---|---|---|
| 아카네 「내일도, 그다음 날도」 | a,a,a,a,a,a,a | 초반 9/0 → 미해금 → 18/0 → 아카네(`o1_shop`) |
| 히나 「처음으로 함께 찍힌 사진」 | b,b,b,b,b,b,b | 초반 0/9 → 미해금 → 0/18 → 히나(`t1_cats`) |
| 코하루 「일요일은 둘이서」 | c,c,c,c,a,b,k | 초반 4/4 → 해금(코하루 4) → 7/7/7 동점 → 가장 최근 개인 선택 k → 코하루(`k1`) |

- 다른 코하루 예: a,b,b,a,k,k,k(초반 5/4 해금, 코하루 4.5 에서 시작), c,c,c,c,k,k,k.
- 해금 플레이에서도 아카네·히나 엔딩에 갈 수 있다(예: c,c,c,c,a,a,a → 아카네, c,c,c,c,b,b,b → 히나).
- 해금 조건은 `c7.ch` 반응 뒤 두 점수 차가 1 이하인 것이다. 해금되면 금요일 복도 첫 만남과 토요일 오전 추첨 장면이 나온다.
- `?debug` 를 붙여 열면 콘솔의 `window.__vn.info()` 로 점수·루트를 볼 수 있다.
- 위 조합의 결과는 `npm run validate -- --paths` 출력에서도 확인했다.

## 5. 저장 호환

### 규칙

- 저장 스키마는 2에서 3으로 올렸다. 신판 저장은 만남 여부(`flags['kh.met']`), 선택 기록, 점수(0.5 단위 포함), 위치를 그대로 복원한다.
- 구판(스키마 1·2) 저장은 불러올 때 다음 규칙을 따른다.
  1. 점수를 지금 대본의 옵션 정의로 선택 기록에서 다시 계산한다. 개인 선택은 +2/+2/+2/+3, 코하루는 0 이다. 장면 진입 스냅샷의 점수도 같이 다시 계산한다.
  2. 위치가 `c7.j20`·`c7.j30`·`c7.j40` 이거나 그 뒤(이미 루트가 있음)면 `kh.met = false` 다. 첫 만남을 소급하지 않는다. 그보다 앞의 공통 저장에는 플래그를 두지 않는다. 그래서 이어서 플레이하면 새 규칙대로 판정한다.
  3. 이미 루트에 들어간 저장은 위치와 루트를 그대로 둔다.
  4. `lastHeroine` 은 선택 기록 순서로 다시 계산한다.
- 선택 직후나 CG 표시 중에 저장했다 불러와도 점수와 CG 관람은 한 번만 반영된다.
- 본 엔딩은 전역 기록(`ashita.global`)과 보조 키(`ashita.global.ext`)에 함께 적는다. 확장 전 빌드가 열린 탭이 전역 기록을 다시 써서 코하루 엔딩을 지워도 남게 하기 위해서다.
- 확장 전 빌드는 스키마 3 저장을 읽지 못한다. '더 새로운 버전…' 안내를 띄운다(README 에 적음).

## 6. 직접 확인(브라우저 1개, 미리보기 서버)

`dist/` 를 `vite preview`(127.0.0.1:4821)로 띄우고 Playwright 라이브러리로 짠 스크립트를 한 번에 브라우저 하나씩 돌렸다. 저장소 스펙과 별개로 실제 화면을 처음부터 눌러 진행했다.

- Chromium 844×390(터치·DSF 2) 새 게임, c,c,c,c,a,b,k(21건 통과).
  - 새 게임 전 타이틀: 앨범 '0 / 11', 엔딩 배지는 아카네·히나 2개, 화면 글자에 코하루·나루세 없음
  - 선택지 7곳 모두 3개 보임: 초반 a,b,c, 후반 a,b,k
  - 금요일 복도 `c7.m20`·`c7.m40`: 이름표 '여학생', 이름표 색은 NPC(`data-who=npc`), `c7.m40` 에 `kh_meet` CG
  - 토요일 점수 4/4/4, 루트 첫 줄 `k1.010` 에서 7/7/7
  - 엔딩 제목 「일요일은 둘이서」, 스크립트 오류 0
- WebKit `iPad (gen 7) landscape`(`data-render='apple-touch'`): 위 플레이의 `k6.170` 자동 저장으로 이어 하기. 고백 CG `kh_confession` 이 그려졌다. 스크립트 오류 0.
- Chromium 1280×720: 새 게임 타이틀에 '0 / 11' 이 보이고 배지는 2개다. 844×390 타이틀에서는 반쪽 버튼의 수를 원래 감춘다(기존 규칙).

## 7. 확인하지 않은 것과 알려진 한계

- **실제 iPad Safari, iPhone, Android Chrome 기기에서는 확인하지 않았다.** 위 결과는 모두 Linux 의 Chromium 과 WebKit 기기 흉내다.
- 실제 기기 성능(프레임·메모리·발열)을 재지 않았다. 코하루 스프라이트가 한 장 평균 약 678KB 로 다른 히로인보다 커서, 느린 망에서 표정 교체가 늦어질 수 있다.
- macOS Safari, Firefox 는 돌리지 않았다.
- 높이 280px 가로 화면(692×280·740×280)의 타이틀에서는 엔딩 배지가 화면 아래로 나간다(배지 위끝 270px, 아래끝 302px). 배지가 2개일 때도 같아서 이번 확장과는 별개인 기존 문제다. 높이 320 이상(740×320, 667×375)에서는 배지 3개도 화면 안에 들어간다. 배치 검사는 높이 320 이상만 본다.
- 선택지에서 고르지 않은 갈래 전용 그림은 받기만 하고 미리 해독하지 않는다. 고른 갈래의 첫 줄에서 해독 시간만큼 기다릴 수 있다. 실제 기기에서 이 지연을 재지 않았다.
