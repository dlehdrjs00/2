# 내일도 같이 갈래? (가제)

일본 학원물 애니메이션 분위기의 짧은 **학원 일상 러브코미디 비주얼노벨** 웹게임 — 플레이 버전(대본 v0.3.0, 세 히로인·여덟 엔딩).
설치 없이 브라우저에서 실행되며 PC와 휴대폰 가로 화면에 맞춰 만들었습니다.

- 주인공 아오야마 소우타(1인칭, 그림 없음)와 두 히로인: 소꿉친구 **미즈하라 아카네**(츤데레) · 전학생 **사쿠라이 히나**. 조건을 만족한 플레이에서만 숨은 후배 **나루세 코하루**(1학년, 이름은 가칭)가 등장합니다.
- 흐름: 공통 이야기(초반 선택 4번 `c3.ch` `c4.ch` `c6.ch` `c7.ch` — 각각 '셋이 함께' 선택 포함) → 금요일 하교 때 숨은 등장 판정(두 히로인 점수 차 1 이하) → 주말·월요일에 함께 노는 에피소드 세 편(토요일 빙수집 · 월요일 점심 종이개구리 대회 · 소나기가 그친 방과 후 처마) → 루트 결정 → 히로인 본편(7/13~7/17) → 결말 갈래 선택 한 번 → 엔딩 8개
  - **코하루를 만난 플레이**: 코하루는 두 히로인 점수의 평균에서 시작합니다. 넷이서 노는 에피소드에서 후반 선택 6번(`e1f.ch1` `e1f.ch2` `e2f.ch1` `e2f.ch2` `e3f.ch1` `e3f.ch2`, 에피소드마다 두 번). 매번 아카네·히나·코하루 중 고른 한 사람에게만 +0.5 입니다('모두' 선택 없음).
  - 여섯째 선택 뒤 한 번 판정합니다. 세 사람 점수가 **완전히 같으면 네 사람(히든) 루트**, 단독 최고점이면 그 히로인, 두 사람만 공동 최고점이면 선택 기록을 최근부터 읽어 그중 가장 최근에 고른 사람입니다.
  - **만나지 않은 플레이**: 셋이서 노는 에피소드(점수 선택 없음)와 기존 후반 선택 3번(`c8.ch` `c9.ch` `c10.ch`, 개인 +3 또는 '함께')을 지나고, 아카네·히나 중 기존 규칙으로 정합니다. 코하루와 히든 루트의 흔적은 나오지 않습니다.
  - **결말 갈래**(7월 17일 금요일, `o4.fork` `t4.fork` `k4.fork` `h.fork`): 축제 쪽과 일상 쪽 중 하나를 고릅니다. 점수·루트에 영향이 없고, 다른 엔딩을 먼저 볼 필요도 없습니다.
  - 점수는 화면에 보이지 않습니다. 엔딩별로 새 게임부터 누를 순서는 [docs/EIGHT_ENDINGS_VERIFICATION.md](docs/EIGHT_ENDINGS_VERIFICATION.md) 3절에 있습니다.

## 실행

Node.js 22 를 권장합니다(배포 워크플로가 22 를 씁니다).

```bash
npm ci             # package-lock.json 그대로 설치
npm run dev        # 개발 서버 http://localhost:5173  (0.0.0.0 으로 열려 같은 네트워크의 휴대폰에서 http://<PC의 IP>:5173)
npm run build      # 타입 검사 후 dist/ 에 정적 파일 생성
npm run preview    # 빌드 결과 미리보기 http://localhost:4173  (0.0.0.0 으로 열림)
```

- 주소 끝에 `?debug` 를 붙이면 브라우저 콘솔에서 `window.__vn.info()` 로 현재 상태(장면·문장 id·루트·점수 등)를 볼 수 있습니다.
- 저장·설정·읽은 대사·본 엔딩·본 CG 기록은 브라우저 로컬 저장소(`ashita.*` 키)에만 남습니다(기기 간 동기화 없음).
  - 본 엔딩은 `ashita.global.ext`·`ashita.global.v2` 에도 한 번 더 적고, 읽을 때는 세 키의 합집합을 씁니다.
  - 이전 빌드가 열린 탭이 전역 기록을 다시 쓰면 자기가 모르는 엔딩을 지웁니다. 코하루 확장 전 빌드는 코하루 엔딩과 새 엔딩 다섯 개를, 여덟 엔딩 확장 전 빌드(`897ae1f` 등)는 새 엔딩 다섯 개를 지웁니다. 그 빌드들이 모르는 보조 키가 기록을 지킵니다.
- 저장 형식은 스키마 4 입니다.
  - 스키마 3(여덟 엔딩 확장 전) 저장은 점수·선택·위치·루트를 그대로 읽습니다. 코하루를 만난 뒤 옛 후반 선택(`c8.ch` `c9.ch` `c10.ch`)을 이미 시작한 진행 중 저장에는 표식(`kh.late3`)을 붙여, 옛 배점(+3)·옛 판정으로 끝까지 갑니다. 이 저장은 히든 루트로 바뀌지 않습니다.
  - 이미 정해진 루트와 기존 클리어 기록도 새 엔딩으로 다시 분류하지 않습니다.
  - 스키마 1·2 저장은 예전처럼 불러올 때 새 점수 규칙으로 다시 계산하고, 이미 노을길 뒤였던 저장에는 코하루 첫 만남을 소급하지 않습니다.
  - 반대로 **이전 빌드 탭은 새 저장을 읽지 못해** '더 새로운 버전의 게임에서 만든 저장 데이터…' 안내와 삭제를 권합니다. 그 탭에서는 지우지 말고 새로고침하세요.
- 저장 공간이 가득 차는 등으로 브라우저 저장소에 쓰지 못하면, 그 값은 **이 탭의 메모리에만** 남고 브라우저 저장소의 이전 값은 지우지 않습니다. 같은 탭에서는 최신 진행을 이어 가고, 새로고침하거나 탭을 닫으면 마지막으로 브라우저에 저장된 위치로 돌아갑니다. 영구 저장 여부는 칸마다 따로 판단합니다(아래 '저장').

## iPad 렌더링과 배경 업데이트 (2026-11-24)

- **Apple 터치 기기(iPad·iPhone)**: iPadOS 의 데스크톱 웹사이트 모드(맥 UA + 터치)까지 `src/ui/render-profile.ts` 가 감지해 `#vn[data-render='apple-touch']` 를 붙입니다. 이때 `src/ui/styles/performance.css` 가 유리 흐림(backdrop-filter)·큰 스프라이트 그림자·흐린 레터박스를 뺍니다(레터박스는 낮·노을·밤 톤별 그라데이션, 흐림이 빠진 대사창·메뉴 카드는 불투명도를 올림). 인물의 톤 보정(노을·밤·말하지 않는 인물·선택지)은 표준과 같고 그림자만 없습니다. 게임 전체 그림은 미리 받지 않고 지금·다음 장면 그림만 받으며, 미리 해독해 붙잡아 두는 그림은 4장입니다(그 밖의 기기 8장).
- **모든 기기 공통**: 스프라이트 filter 전환 보간을 없앴습니다. 무대 해독 캐시(`src/ui/image-cache.ts`)는 최근 8장 또는 해독 픽셀 12Mi(약 48MiB) 안으로 보관하며, 지금 그림 크기로는 픽셀 상한이 먼저 걸려 5~6장입니다. 해독 중인 그림·화면에 붙은 CG·방금 해독한 한 장은 퇴출하지 않아 잠깐 넘을 수 있고, 브라우저 전체 메모리 상한이라는 뜻은 아닙니다. 미리 불러오기가 따로 붙잡는 해독본은 이와 별도입니다.
- 밤 유카타 밝기: 기본 1.04, 말하지 않는 인물·선택지 0.98(세 히로인 모두 — 코하루 k6·k7 포함, 표준·Apple 터치 모두). 지금 대본의 밤 장면은 히로인이 늘 혼자라 0.98 상태는 실제 플레이에 나오지 않습니다.
- 배경 19장을 상세한 WebP(`public/assets/bg/`, 1920×1080)로 바꿨습니다. 같은 장소의 날씨·시간대 변형은 같은 구도입니다. 제작 기록은 `docs/BACKGROUND_PROMPTS.md` 에 있습니다. 저장 칸·엔딩 폴라로이드는 480×270 썸네일(`public/assets/bg/thumb/`, `python3 scripts/bg-thumbs.py` 로 생성)을 씁니다. 예전 임시 SVG 배경은 지웠습니다.
- 저장 데이터에는 배경 경로가 아니라 배경 id 가 들어가므로 이전 저장도 그대로 불러옵니다. 자동 저장 실패 안내는 바뀌지 않았습니다.
- `npx playwright install --with-deps chromium webkit` 후 `npm run test:e2e -- --project=ipad-webkit` 으로 WebKit iPad 흉내에서 엔딩 도달(세 기존 엔딩, 여덟 엔딩 대표 두 판)·저장(구판 저장 포함)·렌더링·자동 저장 실패 안내·코하루 루트(해금 조건·숨김 규칙)·대사창 불투명도를 검사합니다. WebKit 흉내는 실제 iPad 의 성능 측정을 대신하지 않습니다.

  - 숨김 규칙: 미발견 플레이·관람 전 앨범·타이틀에 코하루·네 사람의 이름·칸·배지·그림 요청이 없음, 이름을 밝히기 전 익명 이름표
  - 저장: 저장·불러오기(구판 스키마 2·3 저장 포함), 선택 전후·CG 표시 중·결말 갈래 전후 저장의 한 번만 반영, 손상 데이터 복구, 플레이 중 자동 저장 실패(용량 초과) 안내·새로고침 복원·회복
  - 그 밖: 자동/건너뛰기(새 선택지·결말 갈래에서 멈춤), 입력 중복 방지, 화면 배치(공통 선택지 3개·엔딩 배지 최대 8개 포함), 사용자 대사창 불투명도, 세로 화면 안내, 오디오 실패 시 진행, 새 화면(숨기기·퀵저장·탭 시트·설정) 등
- 최근 전체 실행(여덟 엔딩 확장, 4개 프로젝트): 576건 중 통과 388 · 건너뜀 188 · 실패 0. 건너뜀은 모두 스펙의 프로젝트 제한입니다.
- 뷰포트를 직접 바꾸는 배치 검사·긴 플레이 일부는 `desktop` 에서만 돌고, 휴대폰 전용 검사는 휴대폰 프로젝트에서만 돕니다(그 밖의 프로젝트에서는 건너뜀으로 나옵니다). CDP(Chromium 전용) 입력 검사는 WebKit 에서 건너뜁니다.

### 검증 범위

- 브라우저 E2E 는 Linux 에서 Chromium 3개 화면(데스크톱 + 휴대폰 크기 2개의 모바일 에뮬레이션)과 WebKit iPad 흉내(Playwright WebKit + iPad 기기 설정)로 돌립니다. 여덟 엔딩을 넣은 이 버전(v0.3.0 대본)에서도 4개 프로젝트 전체를 돌렸습니다.
- 이 버전에서 실제로 실행한 명령과 통과·건너뜀·실패 수, 분기 분포, 엔딩별 선택 경로, 추가 분량 추정, CG 9장 화면 확인, 저장 호환은 [docs/EIGHT_ENDINGS_VERIFICATION.md](docs/EIGHT_ENDINGS_VERIFICATION.md)에 적었습니다. 코하루 확장(v0.2.0) 때의 기록은 [docs/KOHARU_VERIFICATION.md](docs/KOHARU_VERIFICATION.md)에 있습니다.
- iPadOS 데스크톱 모드 판별은 WebKit 에서 맥 UA 와 `navigator.platform`·`maxTouchPoints` 를 덮어써 흉내 낸 것입니다.
- **실제 iPad Safari·iPhone·Android 기기, macOS Safari, Firefox 는 검증하지 않았습니다.** 실제 성능(프레임·메모리·발열)도 측정하지 않았으므로, 이번 렌더링 변경으로 iPad 의 끊김이 줄었는지는 실제 기기에서 확인해야 합니다.

## 기능

- **무대와 대사창**: 16:9 무대를 화면에 최대한 크게 놓고, 남는 여백은 배경을 흐려 채웁니다(iPad/iPhone 은 성능을 위해 낮·노을·밤 톤별 그라데이션). 노치(안전 영역)를 피하고, 휴대폰을 세로로 들면 가로로 돌리라는 안내가 뜹니다(세로로 계속하기도 가능). 밤 장면은 대사창이 남색 유리로 바뀝니다.
- **빠른 메뉴**: 대사창 위 테두리에 붙은 탭 — 기록·자동·스킵·퀵저장·퀵로드·숨기기·설정·메뉴.
- **탭 시트**: 저장하기·불러오기·설정·대화 기록을 한 창 안에서 탭으로 오갑니다(←/→ 키로도 이동).
- **저장**: 수동 30칸(5쪽 × 6칸) + 자동 저장(대사·선택지가 바뀔 때마다, 엔딩에 닿으면 지움) + 퀵저장 1칸. 칸마다 저장 당시 무대 썸네일·장면 제목·대사·루트 배지가 보입니다. 타이틀의 [이어하기]는 자동 저장에서 다시 시작합니다. 대사를 고쳐 저장 위치를 찾지 못하면 "그 장면 처음부터" 복구를 제안합니다.
  - **자동 저장을 브라우저에 쓰지 못하면**(플레이 중 저장 공간 부족 등): 그 순간 한 번 경고("…새로고침하거나 탭을 닫으면 최근 진행이 사라질 수 있어요", 7초)를 띄우고, 문제가 이어지는 동안 플레이 화면에 주황 상태 표시 **⚠ 이 탭에만 저장됨**을 계속 둡니다(매 대사마다 알리지 않음). 누르면 위험·브라우저에 남아 있는 위치·해결 방법과 **[지금 다시 저장]**이 나옵니다.
  - 다시 저장에 성공했는데 여유 공간이 거의 없으면(가득 찬 저장소에서도 짧아진 값은 덮어써짐) 표시가 **⚠ 공간 부족 · 저장됨**으로 바뀝니다(그 위치는 실제로 브라우저에 저장됨). 성공·실패가 줄마다 번갈아도 표시 글자만 바뀌고 알림은 다시 띄우지 않습니다. 여유 공간이 생겨 저장에 성공하면 회복 알림을 한 번 띄우고 표시를 걷습니다.
  - 저장 화면의 칸·타이틀 [이어하기]에는 이 탭에만 있는 저장에 **'이 탭에만'** 표시가 붙습니다. 퀵저장·수동 저장 안내도 그 칸 기준이라, 다른 칸이 이 탭에만 있어도 브라우저에 저장된 칸에는 "사라져요"를 붙이지 않습니다.
  - 처음부터 브라우저 저장소를 쓸 수 없으면(사생활 보호 모드·차단, 용량이 0인 저장소) 타이틀에서 알리고, 모든 저장이 이 탭에만 남습니다. 저장 공간이 가득 찬 채로 열면 이전 저장은 그대로 불러올 수 있고, 첫 자동 저장 실패 때 알립니다.
- **대사창 숨기기(H)** · **퀵저장 F5 / 퀵로드 F9**
- **설정**: 글자 속도 · 자동 진행 속도 · 대사창 불투명도 · **글자 크기**(보통/크게/더 크게 = ×1/1.12/1.25) · 배경음/효과음 음량 · 전체화면 · **빛망울 효과**(무대 위 빛망울·햇살 켜고 끄기). 미리보기 무대에서 바로 확인할 수 있고 바꾸면 바로 저장됩니다.
- **대화 기록**: 화자 색 이름표, 독백·날짜 카드·고른 선택지를 모양으로 구분합니다.
- **이벤트 CG 26장**: 주요 장면에서 무대 가득 표시되고, 배경이 바뀌면 자동으로 걷힙니다. 저장·불러오기 때도 복원됩니다.
- **추억 앨범**: 타이틀의 추억 앨범에서 본 이벤트 CG 다시 보기(본 CG 는 전역 기록에 남음).
  - 관람 전 숨김 CG 12장(코하루 6장 · 넷이서 노는 에피소드 3장 · 코하루 일상 엔딩 1장 · 네 사람 엔딩 2장)은 한 번 본 뒤에만 칸·제목·총 장수에 들어갑니다. 보기 전에는 빈칸도 없습니다.
  - '네 사람' 묶음은 그 그림을 하나라도 보기 전에는 묶음 자체가 없습니다.
- **엔딩 폴라로이드**: 엔딩 화면에 엔딩마다 대표 CG 를 폴라로이드로 보여 주고, 본 엔딩 메달과 타이틀의 엔딩 배지가 남습니다.
  - 아카네·히나 엔딩 4개는 처음부터 잠긴 배지로 보입니다. 코하루 엔딩 2개는 코하루 엔딩이나 네 사람 엔딩을 본 뒤에, 네 사람 엔딩 2개는 네 사람 엔딩을 본 뒤에만 보입니다.
  - 그래서 엔딩 수의 분모는 4 → 6 → 8 로 늘어납니다.
- **느린 망**: 그림을 다 받아 해독한 뒤에 무대를 바꾸고 대사를 보여 줍니다(최대 8초. 1.2초 넘게 걸리면 '그림을 불러오는 중…', 기다리는 동안 누르면 기다림만 끝나고 줄은 넘어가지 않음). 이미 보이는 인물의 표정·옷만 바뀐 줄은 1초까지만 기다리고, 그동안은 이전 그림이 그대로 보입니다. 곧 볼 그림은 지금 무대 그림을 받은 뒤 미리 받아 둡니다. 데이터 절약 모드에서는 타이틀 키 비주얼을 작은 그림으로 쓰고 게임 전체 그림을 미리 받지 않습니다. iPad·iPhone 도 게임 전체 그림은 미리 받지 않습니다(지금·다음 장면 그림만). → [UI_DESIGN 6.20](docs/UI_DESIGN.md)
- **웹 앱 매니페스트**: 홈 화면에 추가하면 가로 전체화면으로 열립니다(서비스 워커는 없어 오프라인 실행은 되지 않습니다).

### 대본 작성 규칙 요약

  대사를 추가·삭제해 배열 순서가 바뀌어도 저장이 깨지지 않습니다. 이미 공개한 id 는 바꾸지 마세요.
- 이름은 `{osana}`, `{tenko:는}`, `{me:를}` 처럼 치환 키로 씁니다(조사 자동).
- 이벤트 CG 는 `cg('rain_osana')` 로 띄우고 `cg(null)` 이나 `bg(...)` 로 걷힙니다.
- 수정 후 `npm run validate` 로 연결 오류와 분기를 확인하고 `npm run docs` 로 문서를 갱신하세요.

## 배포 준비

- `vite.config.ts` 의 `base: './'` 로 **상대 경로 빌드**를 합니다. `dist/` 를 어느 하위 경로(예: `https://<사용자>.github.io/<저장소>/`)에 올려도 동작합니다.
  JS/CSS 는 `assets/[name]-[hash].*` 로 나와 배포마다 캐시가 갈리고, `public/` 아래 파일은 이름 그대로 복사됩니다.
- `dist/` 폴더를 정적 호스팅(GitHub Pages, Netlify, 사내 웹서버 등)에 그대로 올리면 링크로 플레이할 수 있습니다.
- GitHub Pages 워크플로 `.github/workflows/deploy-pages.yml` 는 **수동 실행 전용**(`workflow_dispatch`)이라 push 로는 배포되지 않습니다.
  1. 저장소 Settings → Pages → Source 를 **GitHub Actions** 로 바꿉니다.
  2. Actions 탭에서 "Deploy to GitHub Pages" 를 골라 **Run workflow** 를 누릅니다.
  3. 워크플로는 Node 22 에서 `npm ci` → `npm run typecheck` → `npm run validate` → `npm test` → `npx vite build` 후 `dist/` 를 Pages 에 올립니다(E2E 는 브라우저가 필요해 돌리지 않음).
- 여덟 엔딩 확장 빌드는 아직 공개 Pages 에 배포하지 않았습니다. 2026-11-26 기준으로 마지막 배포는 2026-11-24 수동 실행의 커밋 `11612b4`(코하루 확장 전)입니다. → [검증 기록 9절](docs/EIGHT_ENDINGS_VERIFICATION.md)
